# Business logic: passive fire installation records

Status: agreed target scope. Nothing in this document is implemented yet.
Related documents: [03-slice-spec.md](./03-slice-spec.md) (what to build, in order) and
[02-system-design.md](./02-system-design.md) (how it is built).

## Purpose

A personal proof of concept that models, in simplified form, how a passive fire
subcontractor records firestopping work on a construction project. It explores
whether four things work well together for site work with unreliable network:

1. Reference data is maintained through a Java service.
2. That data is downloaded to the web app and used with no network.
3. An installer can take photos and write an instruction for the AI while
   offline; the AI call runs once the network is back.
4. Offline data lives in SQLite on the device, and durable data lives in
   Supabase PostgreSQL.

It is not a compliance product, and the README must not describe it as one.

## Who uses it

| Persona | Role in the code | What they do |
| --- | --- | --- |
| Project manager / office admin | `ADMIN` | Sets up projects and each project's approved firestop systems list |
| Installer on site | `INSPECTOR` | Downloads the job, records each firestop they install, adds photos and an AI instruction, reviews the AI draft |
| Main contractor or other reader | `VIEWER` | Reads records, changes nothing |

The existing role names stay. `INSPECTOR` is the installer.

## Terms

| Term | Meaning |
| --- | --- |
| Project | One construction job, e.g. "Harbour View Apartments" |
| Firestop system | One approved way of sealing a particular kind of opening: a wall or floor type, a service type (pipe, cable bundle), a fire rating, the materials, and the method |
| Approved systems list | The firestop systems a project is allowed to use. Each has a short code such as `SYS-01`, unique within the project |
| Inspection record | The installer's record of one sealed opening: where it is, which system code was used, photos, notes, observations, and the AI draft. The code keeps the name `Inspection` |
| AI draft | Text generated by Gemini from the photos and the installer's instruction. Always a suggestion for a human to review |
| Pending sync | A record that exists only on the device and has not reached the server yet |

## Workflow

1. **Office, online.** The admin creates a project and adds its approved
   systems (code, wall or floor type, service type, fire rating, materials,
   method).
2. **Before going on site, online.** The installer signs in and presses
   "Download for offline". Projects and their systems lists are copied to the
   device.
3. **On site, offline.** For each opening they seal, the installer creates a
   record: chooses the project, types the location, picks the system code from
   the downloaded list, attaches one or more photos, writes notes, and writes
   the instruction for the AI. The record is saved on the device and shown as
   "Pending sync".
4. **Network returns.** The app uploads pending records and their photos
   without the installer doing anything. The server checks the project and
   system code, stores the record, and calls Gemini with the photos and the
   instruction.
5. **Review, online.** The installer reads the AI draft, edits the record as
   needed, and sets its status.

## Rules

**Projects and systems**

- A project code is unique across all projects. A system code is unique within
  its project.
- Codes are short and written in capital letters, digits and hyphens, for
  example `HVA` or `SYS-01`.
- Projects and systems are deactivated, never deleted. An inactive project or
  system cannot be chosen for a new record; records that already use it are
  unaffected.
- Only `ADMIN` can create, change or deactivate projects and systems. Every
  signed-in role can read them.

**Inspection records**

- A record must name one project and one system from that project's approved
  list. The server rejects a record whose system does not belong to the project
  or is inactive.
- When a record is stored, it keeps its own copy of the system's code and
  details. Later edits to the approved list do not change existing records.
- `ADMIN` and `INSPECTOR` can create and edit records; only `ADMIN` can delete;
  `VIEWER` reads.
- Status values stay as they are today: `DRAFT`, `IN_PROGRESS`,
  `ACTION_REQUIRED`, `COMPLETED`. A person sets the status.
- Photo limits stay as they are today: JPEG, PNG or WebP, 10 MB per file, five
  files per upload.

**Offline**

- Only creating new records works offline. Editing existing records, managing
  projects and systems, and signing in need a network.
- The system picker offline shows what was last downloaded. The app shows when
  that download happened.
- A record created offline keeps the time it was captured on the device, which
  is separate from the time it reached the server.
- Nothing is lost silently. A record the server rejects stays on the device,
  marked "Sync failed" with the reason, until the installer fixes or discards
  it. A record that could not be sent because of the network stays "Pending
  sync" and is retried.
- Sending the same record twice (for example after a dropped connection) must
  not create two records.

**AI**

- The AI call needs a network, so for offline records it runs after sync.
- The AI drafts text only. It never sets the status and never states that work
  is compliant. Every draft is labelled as requiring human review.
- If the AI call fails, the record is still stored. The failure is shown on the
  record and the installer can retry.
- With no AI key configured, the service returns a clearly labelled mock draft
  (existing behaviour).

## Known simplifications of real practice

These are deliberate cuts so that the demo stays small and can be run with one
photo of anything. The README should list them.

| Real practice | In this demo |
| --- | --- |
| Each opening gets a numbered physical label before it is photographed | No label numbers; the record has a location and a system code |
| Photos are taken before, during and at completion | Plain photos with no stage |
| Each opening is marked on a floor plan | Free-text location |
| Work is assigned by level and area, driven by the main contractor's programme | No work areas or assignment |
| The subcontractor's supervisor checks records; defects go back for rework | No review or defect loop; the status field only |
| A register is exported at handover, with a PS3 producer statement | No export |

## Evidence behind the model

Supported by published sources:

- Installers number and label penetrations before photographing them, keep
  before/during/completion photos, and complete a register and marked-up plans
  ([NZQA unit standard 31916](https://www.nzqa.govt.nz/nqfdocs/units/pdf/31916.pdf),
  [NZQA skill standard 41266](https://www.nzqa.govt.nz/nqfdocs/skills/pdf/41266.pdf)).
- Installers work from a schedule of tested systems linked to drawings
  ([FPANZ position statement](https://cdn.locomotive.works/sites/61678a458a915800ae74991e/content_entry618b102d087882007c8f9d61/618df7be6b65d5007ce85b88/files/ps-passive-fire-fundamentals.pdf)).
- A real site form records location, fire rating of the surface, treatment and
  register number
  ([Auckland Airport notice](https://corporate.aucklandairport.co.nz/-/media/Files/Airfield-Information/Permit-to-work/060213-Fire-Stopping-Requirement-Notice-fill-on-screen.ashx)).

Not verified:

- The day-by-day site routine and the name "Typical Details Matrix" in
  [workflow.md](./workflow.md), which is an AI-generated answer.
- Product and method pairings in the workflow.md table. Seed data therefore
  uses fictional system entries, so the demo never shows an invented test
  report or product claim as real.
- That offline-first is standard across the industry. Vendors advertise offline
  use; no independent source was found.
